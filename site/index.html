View

Isometric or flat 2D

The Iso switch draws the world as blocks you can tilt your head at — cliffs, trees and roofs have volume. 2D is the plain top-down map, the same thing the game map item shows: one square per block, no sides, no stacking, and about five times cheaper to paint — which makes it the best choice for a big world on a phone.

The structures button adds or removes everything player-made on top of the terrain: tree canopies, walls, roofs. Turn it off to see the raw landscape underneath, or leave it off on mobile to halve the work.

Surface materials

What's actually possible

Short version: a static host gives you a beautiful, fast, read-only map. It cannot give you live players, chat, or editing, because nothing on the other end is running code. Below is the honest breakdown.

Works on GitHub Pages

yes Isometric / top-down map, 2D or pseudo-3D

Tiles or a single heightmap file. Zoom, pan, pinch, block tooltips, waypoints. This page is the proof — it is one HTML file, one CSS file, two JS files and some JSON.

yes Full 3D fly-around

BlueMap renders a real 3D mesh of your world (WebGL, three.js) and ships as static files. It is the nicest result and the heaviest: hundreds of MB to a few GB, tens of thousands of files, hours of first render.

yes Side-by-side dimension switching

Overworld, Nether and End are just separate files or separate tile folders. Nothing special needed.

yes Deep links & sharing

Camera position lives in the URL hash, so #x=120&z=-40&z=8 can be pasted into Discord and opens exactly there.

yes Private repo, public map

Your world files never need to be public. Convert on your own machine (or in a private Action) and publish only the render output.

Possible, with effort

effort Big worlds

GitHub Pages caps the published site at 1 GB; Cloudflare Pages caps deployments at 20,000 files and 25 MiB per file. A 5 km survival world rendered at 1:1 is already several GB. Fixes: render fewer zoom levels, use JPEG/WebP, or move the tiles to Cloudflare R2 (10 GB free, no egress fees) and keep only the HTML on Pages.

effort Names, signs, item frames

Renderers skip entities and block entities, so signs and chest contents are invisible. You can bolt on your own labels: export a small JSON of named points (this page does exactly that for its demo POIs) and draw them as markers.

effort Automatic updates

A GitHub Action can re-render on a schedule and redeploy — that is still "static". It is not live: expect the map to lag by however often the job runs. See Add your world.

Not possible on a static host

no Live player positions

That needs a server polling your Minecraft server's query/RCON port and pushing to browsers. GitHub Pages has no running code. Cloudflare Workers can do it (they are not static), but that is a different, non-free-tier-guaranteed project.

no Editing the world from the map

No writes, no uploading a world through the site, no auth. Any file you drop here stays in your browser tab.

no Block-accurate colours for modded blocks

Mod blocks need a colour table. uNmINeD wants a palette file, BlueMap needs its resource pack. Vanilla renders out of the box; mods are a configuration job, not a click.

Add your world

Three paths, easiest first. You only need one.

Path A — done in 10 minutes

1. Export with uNmINeD

Reads your save folder directly, Java or Bedrock, no server plugin.

# image + interactive web export
unmined-cli web render --world="world" --output="./map" --zoomin=2 --zoomout=4
unmined-cli image render --world="world" --output="preview.png" --trim

Open map/unmined.index.html to check it, then commit the whole map/ folder to your repo and point Pages at it. Done — that is a working map on both phone and desktop.

2. Publish

In GitHub: Settings → Pages → Source: GitHub Actions. This repo already has a workflow that deploys the site/ folder; replace it with your export folder when you have one.

Path B — use this viewer with your data

Feed tilty from your world

Any tool that can produce a top-down surface + height export works. This repo ships tools/regions_to_json.py, which reads .mca region files and writes the JSON this page loads — no Java, no mods, no server.

python3 tools/regions_to_json.py ~/saves/MyWorld -o site/assets/world.json --details
python3 tools/regions_to_json.py ~/saves/MyWorld -o site/assets/nether.json --dimension nether

Then create site/assets/config.json pointing at your files (an example is in the repo). The converter reads the surface heightmap first and only carries blocks above it when you pass --details, which keeps the payload small. Pure Python, no Java, no mods, and it runs on a Raspberry Pi.

Data format (if you build your own)

{
  "name": "My World",
  "dimension": "overworld",
  "bbox": { "minX": 0, "minZ": 0, "width": 512, "depth": 512 },
  "palette": { "grass_block": [7977404, 9126720] },
  "blocks": [ "grass_block", "water", "void", ... ],
  "heights": [ 72, 63, 0, ... ],
  "details": [ [12, 73, 40, "oak_leaves"], [12, 74, 40, "oak_log"] ]
}

blocks and heights are row-major: index = z × width + x. details are extra blocks stacked above a column (trees, walls, lanterns). Keep them sparse — they are drawn last and are the expensive part.

Path C — render locally, publish from CI

Automatic re-render

Keep world files out of Git. Copy them to the runner, run your renderer, publish the output. The demo workflow in .github/workflows/deploy.yml shows the Pages half:

- uses: actions/upload-pages-artifact@v3
  with: { path: site }
- uses: actions/deploy-pages@v4

Where it breaks

Nothing below is a guess. These are the limits you will actually hit, and the workaround for each.

Phones

Full 3D maps can be rough on mobile

BlueMap's viewer is a three.js scene: it needs WebGL2, a few hundred MB of GPU memory, and a steady download. A mid-range Android on 4G will load it, slowly, and will drop frames while flying. Safari on iOS is better than it used to be but still the weakest link.

This page avoids the problem by drawing a heightmap on a 2D canvas — no WebGL, no textures, ~122 KB gzipped for the demo overworld. Panning stays interactive because leaving a bitmap on screen is a blit, and the expensive repaint only happens once the camera settles.

Pinch-zoom fights the page

Set touch-action: none on the canvas and handle two-finger gestures yourself, or the browser will zoom the whole page while you are trying to zoom the map. Also disable double-tap-to-zoom via user-scalable=no… which hurts accessibility, so this page disables only the canvas gesture, not page zoom.

iOS Safari has no 100vh

Use 100dvh for anything full-screen, and keep the map above the home-bar safe area. Header and bottom sheet are sized from the viewport height here for exactly that reason.

Data size

GitHub Pages: 1 GB published site

Hard-ish. Tile maps multiply fast: 1:1 detail on a 10k×10k world is 400 regions × 16 zooms of tiles, each a separate HTTP request. uNmINeD at --zoomin 2 on a small world is already ~3,000 files; the same world at zoomin 4 is ~12,000.

Workarounds, in order of effort: lower --zoomin; export JPEG instead of PNG (5× smaller, slightly soft); serve tiles from Cloudflare R2 behind your Pages site; or drop to a single-file heightmap like this page.

Cloudflare Pages: 20,000 files, 25 MiB each

The file cap is the trap — bandwidth is effectively unlimited, file count is not. R2 has no such limit (10 GB storage free, no egress fees) and can sit on the same custom domain under /tiles/*, so the usual answer for a serious map is: HTML/CSS/JS on Pages, tiles on R2.

Deploys get slow

A 20k-file deploy takes minutes and every re-render re-uploads everything. Render once, keep the output in a release asset or R2, and only redeploy the shell.

What static hosting cannot do

Live player markers, chat, console

All of that needs a process that can reach your Minecraft server. Static hosts serve files and nothing else. Cloudflare Workers, Vercel functions or a €4 VPS can do it — but then you are maintaining a service, with auth, rate limits and a server to keep alive. If you want that experience, install Dynmap or squaremap on the server and host it there instead.

Uploading a world through the website

Tempting: drag a save into the browser, get a map. Doable entirely client-side (this page's estimator does the counting part), but a 2 GB save in a browser tab is a memory problem, and there is nowhere to persist the result without a backend. Keep conversion on your machine.

Entities, mobs, armour stands, your pet

Renderers draw blocks. Entities are a separate data source and none of the static exporters ship them. A plugin-based live map can, which is another reason people run Dynmap.

Privacy & ownership

Your coordinates are public

Anything on Pages is public, even from a private repo. A world map reveals your base, your farms and your ore tunnels to anything that crawls the URL. If that matters: obfuscate the URL, render only explored-but-safe areas with --area, or keep the repo private and publish behind Cloudflare Access.

Nobody updates it for you

Unless you wire CI, the map is a snapshot. A scheduled Action can refresh it, but only from a copy of the world that exists somewhere reachable by the runner.

Verdict

GitHub Pages is enough — start there

For a private-ish survival world, a map like this one or a uNmINeD export fits comfortably in the limits, costs nothing, and lives next to your code. Reach for Cloudflare Pages when you hit 1 GB or want unlimited traffic; reach for R2 when you hit 20,000 files. Only leave static hosting when you need live data — and if you need live data, a proper map plugin on the server is usually the better answer than building one.
